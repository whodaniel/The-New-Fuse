### [2026-07-25] Staging Area May Be Pre-Populated by Another Process — Always `git diff --cached --stat` Before Commit
- **Source**: session
- **Agent**: pi
- **Context**: Phase-1.1 commit of `packages/tnf-cli/src/cli.ts` rename. Ran `git add packages/tnf-cli/src/cli.ts` then `git diff --cached --stat` as the privacy-guard gate. - **Mistake/Failure**: Initial reaction could have been "they were already staged, not my problem, sweep them through." But the 2026-07-21 Privacy Guard rule says stage **only** your work. A pre-populated staging area is the same hazard as `git add -A` — your commit carries files you didn't review. `git reset HEAD` then re-`git add` of the single intended path restored the correct state (`1 file changed, 14 insertions(+), 5 deletions(-)`).
- **Correction/Lesson**: Always treat `git diff --cached --stat` as the first mandatory check after every `git add`. If the listed files are outside the change you intended to land, `git reset HEAD` and re-stage explicitly. - **Codified Rule**: Before `git commit`, run `git diff --cached --stat`. If the file count exceeds the files you explicitly named in `git add`, `git reset HEAD` and re-stage path-by-path. Never rely on the assumption that the staging area was empty when you started.
