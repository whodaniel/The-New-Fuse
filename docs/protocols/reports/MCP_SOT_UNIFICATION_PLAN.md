# MCP Source-of-Truth Unification Plan

**Date:** 2026-08-10
**Status:** PLANNING
**Goal:** Consolidate split MCP configs into a canonical source to eliminate synchronization drift across multiple AI agents and IDEs.

## 1. Current State Assessment

Currently, MCP configuration in TNF is fragmented across several domains:

1. **Canonical Base (`data/mcp_config.json`)**: Generated by `tnf-onboard --repair`. Contains the core TNF local servers (e.g., `tnf-core-server`, `tnf-network`).
2. **Client-Specific Configs (`data/mcp.clients/*.json`)**: Generated by `scripts/tnf-generate-mcp-clients.cjs`. This script duplicates the canonical base for specific agents (`claude`, `gemini`, `cursor`, `pi`, `openclaw`, etc.).
3. **Server Templates (`data/mcp.servers/*.template.json`)**: Contains configurations for external/3rd-party MCPs (e.g., `higgsfield`). These declare environmental prerequisites (like `HIGGSFIELD_API_KEY`) and target clients, but require manual or disjointed scripts to merge.
4. **External Endpoints**: The actual files read by agents live outside the repository in user space (e.g., `~/.gemini/config/mcp_config.json`, `~/.cursor/mcp.json`, `~/.kilocode/mcp.json`).

This split architecture causes friction, as updating one MCP server requires regenerating client configs and manually copying them to external endpoints, leading to drift.

## 2. Proposed Unification Architecture

The unification strategy centers on making `data/mcp_config.json` the **absolute singular source of truth**, and replacing the static file generation with a dynamic, environment-aware sync process.

### Step 2.1: Consolidate the Configuration Manager
Enhance `scripts/mcp-config-manager.cjs` to act as the primary broker for all MCP configuration operations. 
- **Remove** `scripts/tnf-generate-mcp-clients.cjs`.
- **Add a `sync` command** to `mcp-config-manager.cjs`.

### Step 2.2: Dynamic Template Resolution
When `sync` is called, the manager will:
1. Load the base `data/mcp_config.json`.
2. Iterate through `data/mcp.servers/*.template.json`.
3. Check the host environment against `activation.requiredEnv` (e.g., `HIGGSFIELD_API_KEY`).
4. If the requirements are met, dynamically merge the server into the configuration payload.

### Step 2.3: Centralized Endpoint Distribution
Instead of generating generic static files in `data/mcp.clients/`, the `sync` command will directly update or symlink the actual target locations on the host system:
- Cursor: `~/.cursor/mcp.json`
- Gemini/Antigravity: `~/.gemini/config/mcp_config.json`
- Kilocode: `~/.kilocode/mcp.json`
- Claude Desktop: `~/Library/Application Support/Claude/claude_desktop_config.json`

## 3. Implementation Steps

1. **Modify `mcp-config-manager.cjs`:**
   - Add template parsing logic for `data/mcp.servers/`.
   - Add environment evaluation logic (`process.env`).
   - Add a mapping of target agents to their respective physical file paths on macOS/Linux.
2. **Create `tnf mcp sync` CLI mapping:**
   - Map `tnf mcp sync` in `packages/tnf-cli` to invoke the manager.
3. **Refactor Bootstrap Scripts:**
   - Update `factory-boot.sh` and `tnf-start-ai.cjs` to call the new `sync` command instead of the legacy client generator.
4. **Cleanup:**
   - Delete `data/mcp.clients/` directory entirely (prevents confusion).
   - Delete `scripts/tnf-generate-mcp-clients.cjs`.
   - Update `LIVING_STATE.md` to reflect the completed unification.

## 4. Execution Readiness
This plan is ready for implementation. Once authorized by the operator, an autonomous agent can execute these steps sequentially to close the P0-C directive.
