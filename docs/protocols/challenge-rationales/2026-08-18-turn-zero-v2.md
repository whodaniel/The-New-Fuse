## Challenge findings

1. `whodaniel/tnf-monorepo` is the canonical development source; `The-New-Fuse` and `fuse-control-plane` are downstream publication targets.
2. A single three-plane model no longer expresses TNF's product boundary. Work domain, artifact destination, and data residency/sensitivity are independent axes.
3. The current harness is capability-first, so Turn Zero must staff capabilities rather than depend on named agent identities.
4. `apps/frontend/src/data/codebase_map.json` is not a reliable canonical startup input; generated codebase trackers were intentionally removed from version control.
5. ASSIMILATE_CHECK must generalize reusable patterns without propagating private tenant/client/personal context.
6. Host-specific failure-log assumptions (for example Hermes-only paths) conflict with adaptable-host discovery.
7. State freshness must include the canonical development repo and repository/product-boundary receipts, not only the public publication target.
8. Turn End's old handoff schema cannot carry enough context to safely resume cross-repository/capability-first work.

## Baseline versus replacement

**Legacy baseline:** eager/frontloaded orientation plus three work planes, named fleet delegation, fixed codebase-map ingestion, host-specific assimilation scan, and `tnf/session-handoff/0.1`.

**Replacement:** responsive lifecycle `RESPOND -> ORIENT -> CLASSIFY -> HYDRATE -> STAFF -> ACT -> VERIFY -> PROPAGATE -> HANDOFF`, with mutation-time repository and classification gates, task-scoped hydration, capability staffing, privacy-preserving assimilation, expanded freshness receipts, and `tnf/session-handoff/0.2`.

## Safety invariants retained

- Inspect -> Act -> Verify remains mandatory.
- Volatile facts require fresh receipts.
- Destructive/privileged operations retain their existing authority gates.
- Public/private repository separation remains mandatory.
- Personal/client/tenant data cannot be assimilated into public product source merely because a generalized pattern is useful.
- Turn Zero remains non-blocking for ordinary conversation; write readiness is stricter than read/orientation readiness.
